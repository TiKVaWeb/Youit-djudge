# Безопасная очистка и восстановление очереди

Статус: исправления только в форке. Пользователь явно выбрал **не выкатывать**
изменения и не восстанавливать найденную посылку на production в этом запуске.
Production данные и конфигурация не изменялись.

## Подтверждённая причина зависания после сбоя

В `createJudgehostAction()` выражение `j.result != 'compiler-error'` исключало
`NULL`. Но `NULL` — нормальное состояние незавершённой проверки. При перезапуске
host такие задания не возвращались. Кроме того, планировщик удаляет queuetask
после раздачи последнего batch: просто освободить задачи после сбоя недостаточно,
нужно восстановить и запись очереди.

На сервере найден один такой случай: пять незавершённых тестов остаются
назначенными host, запись queuetask отсутствует; остальные тесты этого judging
завершены. Старое состояние по возрасту соответствует перезапуску host. Само
событие, вызвавшее перезапуск, в этом аудите не установлено.

В `JudgehostController.php` подготовлено:

1. Явное включение `NULL`-результатов при регистрации host.
2. Возврат только valid незавершённых tasks этого host; результаты готовых
   тестов и задания других host не изменяются. Invalid/paused tasks не оживляются.
3. Идемпотентное восстановление отсутствующей queuetask с исходным task priority.
   Существующая запись переиспользуется; завершённые обычные judgings не трогаются.
   Явно запрошенная проверка remaining tests продолжает поддерживаться.
4. Один row lock judging для восстановления и удаления очереди планировщиком.
   Перед DELETE очередь повторно проверяется на возвращённые unassigned tasks.

Исправление не назначает вердикты и не перезапускает все проверки заново.
На production оно ещё не применено, найденный случай остаётся для отдельного
согласованного восстановления через штатную логику DOMjudge.

## Что изменено в очистке

- Workdir удаляется не по одному возрасту каталога, а только после read-only
  подтверждения завершённого judging с совпадающим submitid, старым endtime,
  известным результатом, отсутствием queuetask и незавершённых valid tasks.
  Prefetch/debug и неизвестные данные сохраняются. При ошибке/таймауте БД
  удаление прекращается. Рекурсия не следует symlinks и вложенным mounts.
- Удаляются только дочерние numeric judging dirs известного daemon-layout;
  родитель submission, исходники задач, testcase cache, БД и протоколы в БД
  этот cleaner не удаляет. Бюджет — 1000 кандидатов / 200 удалений на запуск.
- Workdir/cache/retention используют `/run/domjudge-maintenance.lock`.
  Очистка scratch не требует остановки judgehost.
- Cache cleaner больше не перезапускает idle host ради нескольких килобайт и
  не сокращает срок warm cache из-за заполненной общей БД. При queued submissions
  host не останавливается. Persisted recovery intent и ExecStopPost защищают от
  оставленного выключенным host после аварийной остановки maintenance script.
  Pending recovery имеет приоритет над workdir cleanup; dry-run не меняет host.
- SQL retention переведён в отчёт: FK `judgetask → judging_run → judging_run_output`
  с `ON DELETE CASCADE` мог удалять диагностическую историю. Нового DELETE нет.
- Убрано ручное обнуление работающих Docker logs и journald. Для будущего rollout
  подготовлена Docker-managed ротация, а не очистка raw JSON files.

Исходные серверные версии сохранены в `baseline/`, их исторические хеши не менялись.

## Read-only замеры production

Срез 19.10.2026, низкая текущая нагрузка; это не нагрузочное тестирование.

| --- | --- |
| Диск | 79 GiB, занято 93%, свободно около 5.7 GiB |
| БД / judgehost scratch+cache | около 64 GiB / 1.2 GiB |
| testcase_content | около 58 467 MiB по InnoDB metadata, уже ROW_FORMAT=COMPRESSED |
| Inodes | занято около 6%, текущего дефицита нет |
| RAM | 7.8 GiB всего, available около 3.5 GiB; swap используется частично |

| Четыре judgehost | enabled, poll age 1–4 s |
| Новые unassigned tasks | 0 в первом срезе |
| Завершённые submissions за последний час | 4; mean queue wait 0.87 s, max 1.32 s |
| Пять последовательных GET /api/v4/info | HTTP 200, 12.6–19.3 ms |
| MariaDB | Threads_running=1, долгих запросов в доступном processlist не видно |

В журнале kernel есть OOM внутри sandbox cgroups отдельных программ. Это
ограничения памяти проверяемых решений, не доказательство общего server OOM.
У всех judgehost `OOMKilled=false`; один прежний restart host остаётся отдельным
историческим событием. Полная информация INNODB_TRX обычному DB user недоступна,
поэтому отсутствие всех возможных транзакционных блокировок не утверждается.

Сейчас нет общей остановки обработки. Но один потерянный judging может не
попадать в обычный счётчик queuetask — мониторить нужно оба состояния.

## Что действительно имеет смысл оптимизировать дальше

1. **Запас места**: увеличение диска/вынос тестового содержимого требуют отдельного
   инфраструктурного решения. Повторный сброс кеша 1.2 GiB не решит рост 64 GiB БД.
   Тесты, задачи и посылки ради освобождения места здесь не удаляются.
2. **Контроль потерянных назначений**: учитывать незавершённые valid judgings без
   queuetask, свежесть poll каждого host, oldest waiting age и реальные времена
   completion. Не использовать безусловный watchdog-restart: он может оборвать
   долгую легитимную проверку. Автоматический мониторинг здесь не устанавливался.
3. **Нагрузочный стенд**: совместно проверить intake/fetch-work, несколько event-feed,
   compile-heavy и long-running задачи, rejudging, interrupted host. Затем выбирать
   количество workers и память PHP-FPM. Просто увеличивать max_children/число host
   при RAM 8 GiB без замеров небезопасно.
4. **Содержимое тестов**: возможный следующий проект — content-addressed хранение
   с дедупликацией и проверкой SHA-256. Экономия пока не измерена; перенос 58 GiB
   и изменение ссылок требуют отдельного аудита и backup. Это не текущий фикс.
5. **Базовый образ**: существующий `ds.so` startup warning нужно отдельно устранить
   при обновлении совместимого PHP base. Его связь с зависанием не подтверждена.

## Выполненные проверки

- 46 Python tests: целостность исторического снимка, cleanup/recovery, symlink,
  inode-swap/mount guards, DB failure, бюджеты, dry-run, SQL NULL semantics,
  запрет destructive retention и raw-log truncation.
- 9 PHPUnit tests, 39 assertions, PHP 8.3 внутри изолированного контейнера:
  NULL selection, queue restoration/idempotency, valid/invalid/finished/other-host,
  explicit remaining tests и повторная проверка очереди под row lock.
- Новый compatibility domserver построен локально как
  `youit-domserver:safety-20261019`; image ID
  `sha256:ad32e30f234af476b65601fcc247d6fa93085c8237d9271d7f20df11e76fc985`.
  PHPUnit запущен также против контроллера, уже включённого в этот образ.
- Shell/PHP syntax, merged Compose validation и bounded logging шести сервисов.
- Исходные 29 server SHA-256 продолжают проверяться; восемь изменённых оригиналов
  теперь адресуются через `baseline_path`, а не заменены новыми хешами.

Полный PHPUnit и реальная конкуренция recovery/scheduler с отдельной MariaDB
здесь не проверялись: PHPUnit использует mocks и не подключается к production.
Это обязательный дополнительный gate перед будущим выпуском PHP-фикса.

## Будущий выпуск — только после отдельного согласования

1. Проверить отдельный тестовый DB-стенд и сценарий host crash/recovery с конкурентной
   выдачей последнего batch. Не повторять этот эксперимент на ученических посылках.
2. Повторно снять текущие hashes/configuration и убедиться, что сервер не изменился.
   Сохранить rollback-копии файлов и конфигурации; DB backup размещать вне почти
   заполненного root filesystem и проверять восстановимость.
3. Установить host maintenance files **вместе с Python helper**, systemd units и
   выполнить dry-run. Не включать архивные скрипты из `baseline/`.
4. Включить новый JudgehostController через постоянный mount либо проверенный image,
   не потеряв остальные overrides. Кратко пересоздать только domserver при выбранном
   варианте; MariaDB и judgehost не перезапускать ради PHP-фикса.
5. Отдельно вернуть подтверждённые потерянные tasks штатной регистрацией idle host,
   проверить, что старые законченные runs сохранены и итог посчитан самим джаджем.
6. Docker logging менять по сервисам отдельным rolling-планом; применение override
   ко всем шести сервисам сразу пересоздало бы и MariaDB, что здесь не допускается.

Обещания «посылки больше никогда не зависнут» нет: этот фикс закрывает найденный
сбой восстановления и конкретные риски maintenance, но не аппаратные отказы,
внешнюю сеть, все возможные ошибки задач и дальнейшее заполнение диска.
