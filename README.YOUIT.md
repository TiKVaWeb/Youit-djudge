# YouIT DOMjudge

Форк [DOMjudge/domjudge](https://github.com/DOMjudge/domjudge) для сопровождения
и оптимизации джаджа YouIT. Исходные лицензии и авторство сохранены;
DOMjudge распространяется под GPL v2 или более поздней версией (см. `COPYING`).

## Базовая версия и ветки

- `youit/9.0.0` — рабочая ветка YouIT от тега `9.0.0`, коммит
  `d8c018e4c6ec050b0089f178976ba1129307beb3`.
- `main` — полученная при создании форка ветка upstream; это **не** наша
  production-ветка и не основание автоматически обновлять рабочий сервер.
- `origin` — `https://github.com/TiKVaWeb/Youit-djudge.git`.
- `upstream` — `https://github.com/DOMjudge/domjudge.git`.

19 октября 2026 через read-only `GET /api/v4/info` работающего сервера
подтверждены DOMjudge `9.0.0`, API v4, environment `prod`.
Это подтверждение версии, а не идентичности исходного кода или образа.
История и теги upstream сохранены. Обновление до `9.0.1` или новой основной
версии должно быть отдельным изменением с проверкой миграций и совместимости.

## Что пока НЕ перенесено с сервера

Создание форка не переносит серверные overrides и не устраняет задержки очереди.
Прямой SSH-доступ к DOMjudge при подготовке форка не прошёл аутентификацию;
актуальные mounts, патчи, image digests и конфигурация сервисов не сверены.

По сохранённым отчётам предыдущих инцидентов требуется проверить:

1. MIME-исправление импорта: `finfo(FILEINFO_MIME_TYPE)` вместо `new finfo()`
   в `ImportProblemService`. В исходном теге `9.0.0` ещё присутствует старый код.
2. Выделенный PHP-FPM pool и nginx-маршрут для streaming event-feed, чтобы
   подключения платформы не вытесняли приём посылок и выдачу работы judgehost.
3. Последовательную очистку кеша только свободных judgehost, сохранение
   работающих обработчиков и защиту от устаревших незавершённых judging rows.
4. Остальные изменения checker/scoring, лимиты загрузки и запуск обработчиков.
   Их наличие и точный diff требуют отдельного аудита текущего deployment.

Эти пункты — список проверки, а не подтверждение текущей конфигурации.
Не копировать в Git `.env`, пароли, токены, дампы БД, посылки и тесты задач.
Deployment-конфигурацию переносить отдельно, без секретов и данных учеников.

## Где дорабатывать

- API и планирование работы: `webapp/src/Controller/API/JudgehostController.php`.
- Приём посылок: `webapp/src/Service/SubmissionService.php`.
- Event-feed: `webapp/src/Service/EventLogService.php`.
- Импорт задач: `webapp/src/Service/ImportProblemService.php`.
- Результаты: `webapp/src/Service/ScoreboardService.php`.
- Проверки webapp: `webapp/tests/`, `webapp/phpunit.xml.dist`.
- Сборка из Git и тестовое окружение: `doc/manual/develop.rst`.

## Порядок дальнейшей работы

Сначала снять read-only inventory production: образы по digest, bind mounts,
overrides, версии БД, PHP-FPM/nginx, judgehost и задания очистки. Сопоставить
каждый патч с исходным тегом и переносить отдельными проверяемыми коммитами.

Далее собрать изолированное Linux-окружение с отдельной БД и синтетическими
задачами. Judgehost запускает недоверенный код: не использовать production-БД,
учебные данные или привилегированный judgehost на рабочем Mac для smoke-теста.

Штатная команда тестов после подготовки окружения по документации upstream:

```sh
webapp/bin/phpunit -c webapp/phpunit.xml.dist
```

Перед оптимизацией измерить ожидание и время проверки, доступность fetch-work
при открытых event-feed, нагрузку БД и объём кеша. Критичные сценарии: несколько
контестов, перепроверка, custom checker, частичные баллы, порядок тестов,
обновление задачи без потери связей с уроками и посылками.

Выпуск — только отдельным действием: проверяемый backup, закреплённый образ,
план отката и rolling-обновление без одновременной остановки всех judgehost.
При создании форка production-сервисы и данные не изменялись; сборка и полный
набор тестов DOMjudge ещё не запускались.
